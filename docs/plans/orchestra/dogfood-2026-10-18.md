# Dogfood run: TripSplit, 2026-10-18

The first dogfood run of the full delivery loop took one idea, a web app that settles shared trip expenses, from a raw pitch to an approved breakdown of 32 stories. It stopped there, by the user's choice, because the run spent most of a 5-hour Pro usage window per two phases and the build would have cost more. The build flow, acceptance and the coach still need their dogfood runs.

## How it ran

The conductor ran headless in its own session, with the project at `~/Workplace/tripsplit` (a local Git repository, no remote), and the overseer played the user, answering its batched questions turn by turn. AskUserQuestion is not available headless, and the conductor fell back to prose questions with a recommendation each, without being told.

| Run | Phases | Findings (high) | Gates |
| --- | --- | --- | --- |
| idea | brief, market research, findings briefing, PR/FAQ | 24 (2) | build rather than adopt Spliit; PR/FAQ approved |
| requirements | brief, PRD, UX design | 47 (3) | PRD v3 (31 requirements, 3 milestones); UX approved |
| architecture | architecture with spikes, breakdown | 46 (3) | architecture approved; breakdown approved |

Every artifact went through a separate checker, and every phase stayed within two rounds of check and revision, bringing what the second round found to the user at the gate. The checkers' findings were substantive: missing competitors and unsupported demand in the research, idempotency for retried edits in the PRD, a phone that goes stale after its own save in the architecture, and stories that touch the same files allowed to run in parallel in the breakdown. Second rounds always found a few new issues that the first round's fixes introduced.

The breakdown meets M2's criterion: stories such as S-1 (container and tooling) and S-9 (settle-up) name the commands, formulas, copy and tests an engineer needs, with dependency edges, and `tasks ready` lists S-1 first.

## What went well

- The conductor classified the request, chained the three flows, kept the run logs complete enough that it resumed cleanly after two usage-limit interruptions, and never opened an artifact.
- A product manager whose context filled wrote its note and handed over to a fresh instance, as designed.
- Roles made and logged their own rulings, and brought to the user only the decisions that changed a requirement or the UX.
- `close-run` surfaced the ledger's signals at each run's end and pointed to the coach.

## What the run exposed, and the fixes

- **Cost of continuity.** Resumed instances carried 250,000 to 370,000 tokens of context, re-read on every tool call, and after a usage-limit wait the expired cache was paid for again in full. The architect who checked the PRD was resumed to author the architecture, carrying a checker's context into a new phase. Fix: the ledger's agent events now record `cache_read_tokens` and `peak_context`, and the conductor's briefing guidance weighs continuity against context size, pauses and runs.
- **Interruptions.** A usage limit stopped running agents mid-step twice. Agents wrote their artifacts at the end, so a stop lost the work in progress. Fix: every authoring role leaves a trail: it writes as it goes and updates its notes file after each major step, which also serves the context-spent handover.
- **Nothing was committed.** Through two flows the living docs and run folders stayed untracked, so engineer worktrees would not have seen the docs. Fix: the conductor commits docs and the run folder locally at each approved gate, and the build's setup checks that the integration branch contains them.
- **Hook gaps.** The first stop of a project's first run wrote no agent event, because the ledger did not exist yet; output tokens were undercounted, because the hook read the first of a streamed message's usage entries rather than the last. Both are fixed, with tests.
- **Headless sessions.** A one-shot `claude -p` exits when the conductor ends its turn and kills any agent still running in the background. A persistent session with stream-JSON input avoids it. This affects how Orchestra is driven, not Orchestra; the README says so.

## Left for the coach

These are proposals to weigh with the ledger's evidence, not fixes made now:

- The recurring signal fired eight times on a first, large run. It groups by skill and category, so the PR/FAQ and the PRD, both written with writing-studio, count as one pattern.
- All 117 findings came from Opus at high effort. A savings trial on the checkers needs a clean streak first; none exists yet.
- Ten of 117 findings were deferred into stories or acceptance criteria at gates rather than fixed, at the user's request to save quota.
