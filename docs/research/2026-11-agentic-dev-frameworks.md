# Agentic development frameworks: what works, what doesn't (November 2026)

Research snapshot taken 2026-11-27, as groundwork for an Orchestra development loop.

Every popular framework enforces its process with prompts, not code, and the most common complaint about all of them is the same: they cost a lot of tokens and add ceremony for gains nobody has measured. Two ideas hold up across every framework and every critic. The first is to keep state in files and git rather than in the conversation. The second is to run each small unit of work in a fresh context and check it with a deterministic test such as a test suite, a type check or a hook, rather than trusting the agent's own claim that it is done. The only peer-reviewed study found (88,052 PRs, ESEM 2026) shows no defect reduction from spec artifacts. No framework treats the human's attention as the scarce resource to budget, and none runs its loop in code while still keeping a human in it. That combination is the opening for Orchestra.

## How much to trust this

Six research agents gathered this from repos, docs, Hacker News, GitHub issues and blogs. Read the claims with four limits in mind:

- **No Reddit or X.** None of the agents could retrieve Reddit or X content, so practitioner sentiment comes from Hacker News, GitHub issues and blogs. This is the largest gap against the brief.
- **Star counts are snapshots.** They come from page loads or third-party trackers on or near 2026-11-27, and the GitHub API was rate-limited for most agents.
- **Cost benchmarks are anecdotes.** Nearly all are single runs, and some come from authors who sell a competing tool. Where two sources disagree, both are noted.
- **Some primary sources were read second-hand.** The ESEM figures came through a summary site, and several Osmani essays were seen only as snippets.

## Matt Pocock's skills

**Mechanics.** The skills are small, composable prompts of a few dozen lines each. The main flow is `/grill-with-docs` (an interview that also writes `GLOSSARY.md` and ADRs), then `/to-spec`, `/to-tickets`, and `/implement` once per ticket with a `/clear` between them. `/implement-spec` instead runs parallel subagents in worktrees. `/tdd`, `/code-review` and `/retro` follow. The phase skills set `disable-model-invocation`, so only a human can start them, and nothing in code enforces the order. The grilling algorithm builds a "design tree" of decisions and, each round, asks every decision whose prerequisites are already settled, each with a recommended answer. It stops only when every branch has been visited. `wayfinder` handles large efforts: it grills breadth-first, keeps a map issue of decision tickets, and resolves one ticket per session. Older AI Hero material paired the skills with Ralph-style `afk` and `once` bash loops, which the current plugin no longer ships. ([repo](https://github.com/mattpocock/skills); local install v1.3.1.)

**What it does right.** The agent finds the facts and the human makes the decisions. Tickets are vertical tracer bullets with blocking links between them. Code review runs two separate subagents, one checking against the repo's standards and one against the spec. The context guidance is concrete: keep the grill, spec and ticket steps inside about 150k tokens, and use a decision tree to choose between continuing, `/clear`, a handoff and a subagent. `/retro` turns repeated mistakes into lint rules or hooks, which is the right direction for enforcement. Because the skills are invoked by the user, they cost about 400 tokens at startup.

**Weaknesses.** Ali's two complaints have direct support. The frontier algorithm can ask low-level questions in the very first round, because it has no early big-picture pass. Users report "12 hours" of "endless, very low level questions" ([#247](https://github.com/mattpocock/skills/issues/247)), "200 questions" ([#44](https://github.com/mattpocock/skills/issues/44)), and an overly detailed grill that "can become a hindrance" ([#644](https://github.com/mattpocock/skills/issues/644)). One user built a lean-grill skill that parks risks which block nothing ([eimerreis.de](https://www.eimerreis.de/writing/the-lean-grill-skill)). The maintainer has rejected a cap on questions and the native question tool; the repo's out-of-scope notes say that "natural-language steering is the intended control surface", so hand-holding is a deliberate choice. In one single-run test the skills matched plain Claude Code on correctness at 1.5 to 4 times the cost ([aiparabellum](https://aiparabellum.com/matt-pocock-skills-claude-code-install-test/)). Defenders say grilling surfaces requirements and removes complexity, and the same test rated grill-me the most useful skill it tried.

## Addy Osmani's agent-skills

**Mechanics.** Osmani is a Member of Technical Staff at Anthropic working on Claude Code, after about 14 years at Google ([bio](https://addyosmani.com/bio/)). `addyosmani/agent-skills` holds 26 skills, 10 commands and 5 reviewer personas. Specs live in `spec/SPEC-<module>.md`, with delta specs for later changes. The plan is `tasks/plan.md` and the task list is `tasks/todo.md`, and each task carries acceptance criteria and a verification step. The spec skill tells the agent to stop its turn after saving the spec. `/build auto` asks for one plan approval, then runs TDD and a commit for each task without stopping. The only state is committed files and git, and there is no resume guidance ([repo](https://github.com/addyosmani/agent-skills)).

**What it does right.** Each skill has an anti-rationalization table and ends by demanding evidence: "Seems right" is never enough. A router loads skills in stages instead of all at once. The spec always describes the current system, and ideas raised mid-build go to a deferred list rather than into scope.

**Weaknesses.** Osmani writes that "the scaffolding has to be enforced rather than suggested", yet nothing in the pack blocks a phase transition. Its `/review` command collides with the built-in one, and running it alongside Superpowers gives "two competing rulebooks" ([reviewramble](https://www.reviewramble.com/github-repos/addy-agent-skills)). Hacker News reaction was mixed: "Skills are just prompt templates", and "After accounting for token costs, it ends up being a wash" ([HN](https://news.ycombinator.com/item?id=48015397)).

**His essays matter more for Orchestra than the pack.** "The Code Agent Orchestra" ([2026-03](https://addyosmani.com/blog/code-agent-orchestra/)) argues that generation is no longer the bottleneck and that you should not run more agents than you can review, which he puts at 3 to 5. It also recommends one reviewer agent for every 3 or 4 builders in front of the human, gating on the plan because a bad plan is cheaper to fix than bad code, stopping and reassigning after 3 failed attempts on the same error, and never letting two agents edit the same file. "Agentic Code Review" ([2026-06](https://addyosmani.com/blog/agentic-code-review/)) moves the human from "in the loop" to "on the loop": tier review by risk, treat AI review as a sensor rather than a verdict, and keep a human owning the merge. A later piece on the "orchestration tax", reported second-hand ([TokenPost](https://www.tokenpost.com/news/technology/47541)), warns that more agents can grow the queue of unreviewed work without growing the capacity to approve it.

## Superpowers

**Mechanics.** Jesse Vincent launched Superpowers on 2025-10-09, the day Claude Code plugins shipped ([post](https://blog.fsck.com/2025/10/09/superpowers/)). Version 7.0.2 has 15 skills totalling about 22k words. Brainstorming produces a dated design doc behind a hard gate: nothing is built until the human approves it. The plan gives exact files, interfaces and failing tests for each task. Execution runs a fresh implementer subagent per task, followed by spec and quality reviewers, a fix loop capped at 5 rounds (escalating to a stronger model in rounds 4 and 5), and a final review of the whole branch. Once execution starts the agent is told not to pause ("Rulings, not stalls") except for irreversible, security-sensitive or externally visible actions. A session-start hook re-injects the bootstrap on startup, `/clear` and compaction, inside an `EXTREMELY_IMPORTANT` block with a "1% chance means you must invoke the skill" rule. Bash helpers keep a progress ledger whose task-done step records a task as complete only if its test command exits 0 ([repo](https://github.com/obra/superpowers)).

**What it does right.** It tests its own skills: release notes cite blind-graded runs, for example cutting filler questions in brainstorming from 41 to 23 between two versions. It passes artifacts to subagents as files, picks a model for each dispatch, and keeps a ledger that survives compaction. The skill's own notes name the most expensive failure they have seen, a controller that lost its place and re-ran completed tasks, and the ledger exists to prevent it.

**Weaknesses.** Whether skills fire is up to the model: open issues show skills skipped because the model judged a task "simple" ([#54](https://github.com/obra/superpowers/issues/54)), bypassed in plan mode ([#1667](https://github.com/obra/superpowers/issues/1667)), or not loaded because the hook failed ([#1465](https://github.com/obra/superpowers/issues/1465)). The opposite failure, worktrees and plans for trivial tasks, is also reported. Users cannot opt in per task. Hacker News comments include "burning too many tokens to do too little", "did materially worse across all my personal benchmarks", and "fills up the context windows with garbage" ([HN](https://news.ycombinator.com/item?id=48739459)). Fans praise its TDD discipline and brainstorming. No independent controlled benchmark exists.

## Ralph loop

**Mechanics.** Geoffrey Huntley presented the technique in June 2025 and wrote it up on 2025-07-14 ([ghuntley.com/ralph](https://ghuntley.com/ralph/)). It is a bash `while` loop that feeds the same `PROMPT.md` to a fresh agent process on every iteration. A human writes the specs up front. Each iteration picks one task from a prioritized fix plan, and tests, types and linters reject bad output. Only files and git carry state between iterations. The variants are snarktank/ralph (`prd.json` stories with a `passes` flag), ralph-orchestrator (Rust, with multiple backends and a Telegram human-in-the-loop channel), and Anthropic's stop-hook plugin.

**What it does right.** The outer loop is deterministic code, so the model cannot argue its way to "done": the stop condition is code checking code, every run can be reproduced, and recovering from a crash means restarting the loop. A fresh context per iteration avoids context rot. It produced striking greenfield and porting results, such as the CURSED language and a hackathon team that ported 6 repos with more than 1,000 commits overnight.

**Weaknesses.** Output quality is capped by spec quality, and errors compound without a human. The agent re-implements code that already exists, writes placeholders, stalls silently on permission prompts or exhausted credits, and passes tests while still violating the spec. Vague goals produce dozens of directionless iterations. Anthropic's plugin keeps one session, which gives up the fresh-context benefit, and critics say it degrades after 3 or 4 iterations ([AI Hero](https://www.aihero.dev/why-the-anthropic-ralph-plugin-sucks)). Tom Wojcik, who mostly stopped using it, put it this way: "validation is the bottleneck" ([2026-01](https://tomwojcik.com/posts/2026-01-15/ralph-claude-code/)).

**Status.** It peaked between December 2025 and January 2026. By mid-2026 the idea had been renamed "loop engineering" and productized as `/loop` and `/goal`. `/goal` uses a small model that reads the transcript to decide when to stop, which drops Ralph's code-checks-code stop condition ([ralph-to-goal](https://thinhdanggroup.github.io/ralph-to-goal/)). Practitioners now use loops only for narrow work whose completion a machine can check.

## GSD (Get Shit Done)

**Mechanics.** Lex Christopherson (TÂCHES) started GSD in December 2025. A thin orchestrator never touches source code. It dispatches researcher, planner, plan-checker, executor and verifier subagents, each in a fresh context, on plans of 2 or 3 tasks sized to about half a context window. Work runs as phases (discuss, plan, execute, verify, ship) grouped into milestones. State lives under `.planning/`: `PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STATE.md` (read first by every workflow), plus a context, plan, summary and verification file for each phase. Pause and resume write `HANDOFF.json` ([GSD Core docs](https://github.com/open-gsd/gsd-core/blob/main/docs/explanation/context-engineering.md)). GSD 2, now GSD Pi, moves orchestration into a TypeScript state machine on the Pi SDK. It opens a new agent session for every dispatch and adds stuck detection, timeouts and a cost ledger ([architecture](https://getshitdone.help/dev/architecture/)).

**What it does right.** It is the only one of the five built for multi-day work across many sessions. Its verification works backward from the goal, checking that requirements and decisions are covered rather than only that tests pass. It offers quick and fast modes as escape hatches. Its user praise comes on complex tasks: "consistently gets me 95% of the way there" ([HN](https://news.ycombinator.com/item?id=47417804)).

**Weaknesses.** It is the most expensive of the five. Users report using up a Max-20x weekly limit in two days, and one removed it "because of token burn" ([#793](https://github.com/gsd-build/get-shit-done/discussions/793)). In one benchmark GSD 2 took about 90 minutes and $27 against under 5 minutes for plain Claude Code, which also produced the better UI ([Chase AI](https://chaseai.io/blog/gsd2-vs-claude-code-which-ai-coding-tool-wins)). A secondary source restates that test with different figures. The fork documents about 89 commands, and users call it "overengineered" with "an insane amount of files". Native plan mode can bypass it entirely ([#336](https://github.com/gsd-build/get-shit-done/issues/336)). Its stewardship also failed: the author went silent, a crypto token caused controversy, the repo was archived on 2026-06-26, and the community forked it ([Discussion #109](https://github.com/open-gsd/gsd-core/discussions/109)).

**Does context rot still matter?** It is reduced but not solved. Long-context retrieval scores have improved, but guides still recommend subagents and active context management ([InfoQ](https://www.infoq.com/news/2026/03/opus-4-6-context-compaction/)). Fresh subagents and file-based state are the parts of GSD likely to survive better models. Its ceremony is what native plan mode, compaction and larger windows are replacing.

## Other tools worth knowing

- **OpenSpec** (Fission AI) keeps the current specs in `openspec/specs/` and puts a small delta spec for each change in `openspec/changes/`, archived on merge. It is designed for existing codebases, has the lightest token footprint, and the Thoughtworks Radar moved it from Assess to Trial ([Radar](https://www.thoughtworks.com/radar/tools/openspec)). Its specs are unverified markdown, so they can drift from the code.
- **GitHub Spec Kit** runs constitution, specify, plan, tasks and implement, and reached v1.0 in August 2026 with a step that reconciles the spec with the code. Critics find it heavy: one feature produced 8 files and about 1,300 lines of docs ([Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)), and one test measured it at about 10 times slower than iterative prompting ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)).
- **AWS Kiro** is an IDE that writes requirements, design and task specs, with event-triggered hooks and steering files. Böckeler found it the lightest of the three tools she reviewed, yet it turned a small bug into 4 user stories with 16 acceptance criteria.
- **BMAD** runs agile personas (analyst, PM, architect, developer) as agents. It is the heaviest and slowest of these tools and is widely called overkill for small teams.
- **Tessl** bet on "spec as source", where the spec rather than the code is what you maintain. It pivoted to a skills registry in January 2026 before that framework reached general availability. Agent OS likewise dropped its orchestration phases in v3 and now only injects coding standards, using Claude Code plan mode for specs. Both retreats are evidence against heavy process.
- **Taskmaster** turns a PRD into a dependency-ordered `tasks.json`. It has been quiet since April 2026 (unverified).
- **Beads** (Steve Yegge) is a git-backed issue graph for agents, with hash IDs and detection of which work is ready to start. Agents can be killed after each issue because the graph re-injects decisions ([essay](https://yegge.ai/essays/introducing-beads-a-coding-agent-memory-system/)).
- **Anthropic's long-running harness pattern** uses an initializer agent that writes an init script, a progress file and a feature list of 200 or more items, all marked failing. Each later session implements one feature, flips only its `passes` field and commits ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). It is the clearest published answer to multi-day work.
- **Code-driven orchestrators.** Claude Code dynamic workflows run a script that decides what happens next, so intermediate results stay in variables rather than in context and outputs are validated against schemas ([docs](https://code.claude.com/docs/en/workflows)). They resume only within a session, so they are no store for multi-day work. Archon runs YAML pipelines that mix bash steps with AI steps, plus approval gates and a worktree per run ([repo](https://github.com/coleam00/Archon/tree/dev)). Open SWE on LangGraph has a human plan-approval interrupt and durable thread state. Stop hooks that block completion until tests pass are the smallest deterministic gate. One pitfall: the hook must exit with code 2, because a plain `exit 1` never reaches Claude.

## What they have in common

All of them separate deciding what to build from building it, and put a human approval at that boundary, usually on a spec, design doc or plan. All of them keep the durable artifacts (spec, plan, tasks, progress) as markdown or JSON in the repo, because the conversation does not survive across sessions. All the newer ones split work into small tasks, give each a fresh subagent context, and review each with a separate subagent. All of them use TDD or a test command as the main evidence that work is done. All of them, except Ralph's outer loop and GSD Pi, rely on the agent to follow the process, and every one has open issues where it did not.

## Where they differ

The first difference is **who drives**. In Pocock's skills the human drives every transition (pull). Superpowers and Osmani's pack let the agent drive once a plan is approved, with a hook pushing the skills into context. Ralph and GSD Pi let code drive. In between, the human loses steering in exchange for autonomy, and nobody offers code-driven steps with the human gates kept explicit.

The second is **where the human spends attention**. Pocock spends it up front, in long interviews. Superpowers and Osmani spend it on one design or plan approval, then step away. Ralph spends almost none during the run and all of it on recovery. GSD spends it at every phase boundary. None budgets human attention or batches decisions to minimize interruptions, and only Osmani's essays treat review capacity as the binding constraint.

The third is **the unit of state across sessions**. Pocock uses issue-tracker tickets, GSD uses a `.planning/` tree with a single `STATE.md`, Superpowers uses a plan with a git-ignored ledger, Ralph uses a PRD with `passes` flags, and Osmani uses only files. GSD and Anthropic's harness are the only ones built for work spanning days and many sessions.

The fourth is **weight**. They range from about 400 tokens of startup cost (Pocock) and OpenSpec's small deltas, through Superpowers' 22k words, to GSD's dozens of commands and agents and BMAD's personas. User sentiment tracks weight closely: the heavier the framework, the more often "token burn" and "plan mode is enough" appear in its reviews.

## Evidence, kept apart from opinion

**Measured.** The peer-reviewed ESEM 2026 study of 88,052 PRs across 119 repos found no defect reduction from spec artifacts once task complexity is controlled for (0.6 percentage points, p=0.133) ([Dagstuhl](https://drops.dagstuhl.de/entities/document/10.4230/LIPIcs.ESEM.2026.84)). It measured linked spec documents, not framework workflows. The ETH study on AGENTS.md found context files gave no gain in task success and raised cost by more than 20%, and LLM-generated context files were the worst ([ETH SRI](https://www.sri.inf.ethz.ch/publications/gloaguen2026agentsmd)). A 2026 adherence study found that agents follow context-file instructions in a polarized way, some always and some never ([arXiv 2611.13709](https://arxiv.org/abs/2611.13709)). A Spec Kit preprint reports small gains: +0.15 on a 1-to-5 quality score judged by an LLM, and +1.7% on SWE-bench Lite. A preprint on specs used for test generation reports +9.8 percentage points in bug detection. An audit of a gated workflow found that the orchestrator judging its own work was the weak point. METR's 2025 trial found experienced developers 19% slower with AI, and METR now calls that result outdated without having reliable newer data.

**Anecdote.** Every cost and speed comparison between frameworks is a single run, and several conflict with each other. They agree only on direction: heavier frameworks cost more time and tokens on small and medium tasks, and nobody has shown a quality gain that pays for it.

**What practitioners converge on for good results at low token cost:** small delta specs or a single plan in plan mode instead of a heavy spec suite; short hand-written context files instead of generated ones; deterministic checks (tests, types, Stop hooks, scripted workflows) in place of instructions; and a task graph or ticket store outside the conversation for work spanning sessions.

## Implications for Orchestra

These are positions to argue from, grounded in the findings above.

1. **Put the loop in code and keep the human in it.** Every prompt-only framework has open issues where the agent skipped a gate. Ralph and GSD Pi show that code-driven loops are reliable, but they push the human out. A script that owns sequencing, state and gate checks, and calls agents only for judgment work, is the combination nobody has shipped, and it matches the determinism Ali wants.
2. **Treat human attention as the budget.** Osmani's review-capacity argument and the grilling complaints point the same way. The loop should batch decisions, settle the big picture before details, and route only decisions that need the human. Grill breadth-first by default, the approach Pocock reserves for huge efforts, and park details that block nothing.
3. **Make multi-day work the primary use case.** GSD's `STATE.md` and pause/resume, Anthropic's feature list with `passes` flags, and Beads' graph that survives killed sessions are the prior art. A repo-resident state file that a script reads and writes beats one the agent is asked to maintain.
4. **Stay light.** Sentiment against heavy frameworks is the strongest signal in the research, and Tessl and Agent OS retreated from heavy process. Prefer delta specs over full spec suites, few artifacts, and tiny per-step context.
5. **Gate "done" on checks, not on a model's opinion.** `/goal`'s judge reading the transcript, and the audit finding that self-judging orchestrators are weak, are cautionary tales. Tests, a ledger that requires passing tests, and a separate spec reviewer are the proven mechanisms.
6. **Expect the platform to absorb features.** Plan mode, `/goal`, `/loop` and dynamic workflows absorbed much of what the frameworks offered within a year. Build Orchestra on those primitives rather than re-implementing them, and keep its own value in sequencing, state and human-attention policy.
